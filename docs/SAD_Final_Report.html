1. Introduction

1.1 Purpose

This Software Architecture Document (SAD) describes the complete architectural design of the Smart IT Service Request and Support Ticket System for WSiT (World Systems for Information Technology). It serves as the primary technical reference for the development team, academic evaluators, and future maintainers of the system.

Version 2.0 extends the Phase 1 MVP baseline by introducing production-ready security, a Technician role, search capabilities, deployment configuration, and formal Development and Deployment Views.

1.2 Scope

This document covers both Phase 1 and Phase 2 of the system:

  • Phase 1: Customer self-service ticket submission, role-based access (Customer/Admin), ticket lifecycle management, React SPA frontend, FastAPI backend, SQLite database.
  • Phase 2: JWT-based authentication, bcrypt password hashing, Technician role with dedicated dashboard, ticket search and filter by status/priority/keyword, environment-based configuration, Docker containerisation, production deployment architecture.

1.3 Target System

The system is deployed as a web application accessible via any modern browser. The backend exposes a JSON/HTTP REST API consumed exclusively by the React frontend. In production, Nginx acts as a reverse proxy routing traffic to either the frontend static files or the FastAPI backend.

1.4 Architecture Style: Layered REST API

The system implements a four-layer architecture with strict separation of concerns:

LayerTechnologyResponsibility
PresentationReact 18, Vite 5Renders UI, manages local state, calls API
Controller (API)FastAPI route handlersValidates requests, enforces auth, delegates to services
Business LogicService modules (Python)Enforces rules, orchestrates data operations
Data AccessSQLAlchemy 2.0 ORMAbstracts SQLite queries behind repository functions

The document follows the 4+1 Architectural Model (Kruchten, 1995): Use Case, Logical, Process, Development, and Physical (Deployment) Views, plus a Scenarios (+1) View.

2. System Selection

2.1 System Name & Description

Smart IT Service Request and Support Ticket System

WSiT provides managed technology services across multiple verticals. Customers previously reported issues via email and phone, resulting in untracked requests, missed SLAs, and poor visibility. This system replaces the informal process with a structured, digital ticketing workflow accessible 24/7 through a web browser.

3.2 Logical View

3.2.1 Layer Breakdown

Presentation Layer — React SPA

  • LoginPage.jsx — Login/Register tabs with Customer/Technician role selector, loading/error states
  • CustomerDashboard.jsx — Ticket submission form, status/priority filter bar, ticket list
  • AdminDashboard.jsx — Search input, status/priority filters, technician assignment dropdown, inline status controls
  • TechnicianDashboard.jsx — Assigned ticket list, resolve/close action buttons, filter bar (Phase 2)
  • TicketDetails.jsx — Read-only single ticket view with all metadata
  • Navbar.jsx, StatusBadge.jsx — Reusable UI components
  • api/client.js — Centralised Axios instance with JWT Bearer token interceptor and VITE_API_URL configuration

Controller Layer — FastAPI Routes

  • routes/auth.py — POST /auth/login (issues JWT), POST /customers/register (Customer/Technician), GET /technicians (admin dropdown)
  • routes/tickets.py — All ticket endpoints with JWT dependency; optional ?status, ?priority, ?search query params on list endpoints; PUT /tickets/{id}/resolve for technicians

Business Logic Layer — Services

  • services/auth_service.py — bcrypt hashing/verification, JWT creation/decoding, admin seeding, technician list retrieval
  • services/ticket_service.py — Ticket CRUD, _apply_filters() helper for keyword/status/priority queries, get_tickets_by_technician()

Data Access Layer — SQLAlchemy + Config

  • models/models.py — User ORM (roles: customer/technician/admin), Ticket ORM, TicketStatus, TicketPriority, ServiceType enums
  • schemas/schemas.py — Pydantic request/response contracts for all endpoints
  • database/database.py — SQLAlchemy engine, SessionLocal, get_db dependency; reads DATABASE_URL from config
  • core/config.py — Loads SECRET_KEY, ALGORITHM, ACCESS_TOKEN_EXPIRE_MINUTES, DATABASE_URL from .env via python-dotenv (Phase 2)

3.3 Process View

3.3.1 Key Workflows

JWT Login Flow (Phase 2)

  1. User submits email + password to POST /auth/login
  2. auth_service.verify_password() checks bcrypt hash stored in DB
  3. On success, auth_service.create_access_token() generates a signed HS256 JWT
  4. JWT payload: {"sub": user_id, "email": ..., "role": ..., "exp": ...}
  5. Frontend stores JWT in localStorage; Axios interceptor attaches it as Authorization: Bearer <token> on all subsequent requests
  6. React Router redirects to /dashboard, /technician, or /admin based on role

Ticket Submission Flow (Customer)

  1. Customer fills the service request form on CustomerDashboard
  2. Axios POSTs to POST /tickets with Authorization: Bearer <JWT>
  3. get_current_user() dependency decodes JWT, retrieves user by sub (ID) from DB
  4. ticket_service.create_ticket() writes a new Ticket row (status = open)
  5. Response returned; ticket appears in the customer's list

Technician Assignment & Resolution Flow (Phase 2)

  1. Admin opens dashboard → GET /tickets (all tickets) + GET /technicians (dropdown)
  2. Admin selects technician from dropdown → PUT /tickets/{id}/assign
  3. ticket_service.assign_ticket() → assigned_technician = name, status = in_progress
  4. Technician logs in → GET /tickets/assigned shows only their tickets
  5. Technician clicks "Mark Resolved" → PUT /tickets/{id}/resolve with status = resolved
  6. Backend verifies assigned_technician == current_user.full_name before updating
  7. Technician clicks "Mark Closed" → status = closed

Search & Filter Flow (Phase 2)

  1. User selects filters (status, priority) or enters a keyword in the UI
  2. Frontend calls GET /tickets?status=open&priority=high&search=floor
  3. ticket_service._apply_filters() applies SQLAlchemy WHERE clauses and ilike() for keyword search
  4. Filtered list returned and rendered in the table

3.5 Deployment View (Physical View)

3.5.1 Development Deployment (Local)

All services run on a single developer machine. The browser communicates with the Vite dev server (port 5173) which serves the React SPA. All API calls are directed to FastAPI/Uvicorn on port 8000. FastAPI reads and writes to a SQLite file on the local filesystem. Environment variables are loaded from backend/.env.

3.5.3 Production Deployment (Docker + Nginx)

In production, the system is containerised with Docker. The React application is pre-built into static files and served by Nginx. FastAPI runs behind Uvicorn inside a Python container. An Nginx reverse proxy acts as the single entry point: static assets are served directly while API requests (/api/*) are proxied to the FastAPI container.

ComponentContainerPortResponsibility
Nginx reverse proxynginx:alpine80 (external)Routes: / → frontend, /api/* → backend
React frontendnode:18 → nginx:alpine80 (internal)Serves pre-built static SPA files
FastAPI backendpython:3.11-slim8000 (internal)Handles all REST API requests
SQLiteDocker volume—Persists ticket and user data

3.5.5 Nginx Reverse Proxy Configuration (Reference)

server {
    listen 80;
    server_name _;

    location / {
        proxy_pass         http://frontend:80;
        proxy_set_header   Host $host;
    }

    location /api/ {
        rewrite ^/api/(.*) /$1 break;
        proxy_pass         http://backend:8000;
        proxy_set_header   Host $host;
        proxy_set_header   X-Real-IP $remote_addr;
    }
}

3.6 Scenarios (+1 View)

Scenario 1 — Customer Logs In and Submits a CCTV Request

  1. Customer registers at /login with role "Customer" → account created with bcrypt hash
  2. Customer logs in → POST /auth/login → JWT issued → navigated to /dashboard
  3. Clicks "+ New Request", selects CCTV, priority High, fills title/location/description
  4. POST /tickets → JWT decoded → ticket_service.create_ticket() → status = open
  5. Ticket appears in "My Service Requests" table

Scenario 2 — Admin Assigns a Technician and Searches

  1. Admin logs in with admin@wsit.com / admin123 → navigated to /admin
  2. Types "CCTV" in search box, selects Status = open → GET /tickets?search=CCTV&status=open
  3. _apply_filters() applies ilike and WHERE → filtered list returned
  4. Admin selects "Ahmed Al-Rashid" from technician dropdown → clicks Assign
  5. PUT /tickets/1/assign → assigned_technician = "Ahmed Al-Rashid", status = in_progress

Scenario 3 — Technician Resolves an Assigned Ticket

  1. Technician registers at /login with role "Technician" → account created
  2. Technician logs in → navigated to /technician dashboard
  3. GET /tickets/assigned → shows only tickets where assigned_technician == full_name
  4. Technician clicks "Mark Resolved" on ticket #1
  5. PUT /tickets/1/resolve → backend verifies ownership → status = resolved
  6. Technician clicks "Mark Closed" → status = closed

Scenario 4 — Customer Tracks Ticket Status

  1. Customer logs in, applies filter Status = resolved
  2. GET /tickets/my?status=resolved → filtered list of own resolved tickets
  3. Customer sees ticket #1 with technician "Ahmed Al-Rashid" and status resolved
  4. Customer clicks "View" → TicketDetails shows all metadata and description
